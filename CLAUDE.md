# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

ArduPilot ROS2 Swarm - A scalable drone swarm simulation system combining ArduPilot SITL with ROS2 for autonomous multi-drone operations using Docker containers.

## Essential Commands

### Starting the Swarm
```bash
# start_swarm.sh takes ONLY a drone count (no build flag). Default is 2.
./start_swarm.sh 4     # Start with 4 drones
./start_swarm.sh 8     # Start with 8 drones

# Rebuild images after Dockerfile/dependency changes, then start
docker compose build
./start_swarm.sh 4

# Check swarm status
./src/scripts/check_swarm_status.sh 4  # Check status for 4 drones
```

`start_swarm.sh` first brings up `discovery_server` + `swarm_controller` via
`docker compose up -d`, then loops `docker compose run -d` per instance to launch the
`drone_ardu` and `micro-ros-agent-drone` services (both gated behind the `manual` compose
profile), naming containers `drone-ardu-<i>` and `micro-ros-agent-drone-<i>`.

### Gazebo Visualization (optional)
```bash
# Start Gazebo FIRST (host GUI; --headless for server only), THEN the swarm:
./start_gazebo.sh &
USE_GAZEBO=1 ./start_swarm.sh 4
```
`USE_GAZEBO=1` switches SITL physics to Gazebo's JSON FDM backend (`--frame
gazebo-iris --model JSON`); each drone model in `src/custom_gz/worlds/swarm_drone.sdf`
binds FDM port `9002 + 10*instance` via a dedicated model dir
(`src/custom_gz/models/base_drone{,_1,_2,_3}`) — SDF `<include>` cannot override a
nested plugin's port, so the port is baked into each model. In Gazebo mode the
container startup appends `gazebo-iris.parm` (X-frame) after `dds_swarm.parm`;
without it the plus-frame mixing produces no lift while the mission runs open-loop.
Requires the ardupilot_gazebo plugin build on the host (paths set in `start_gazebo.sh`).

Verify flight by actual `rel_alt` gain (pymavlink on UDP `14550+instance`), never by
takeoff service ACKs — those succeed even if the vehicle stays on the ground.

Gotcha: QGroundControl's virtual joystick (`virtualJoystick=true` in
`~/.config/QGroundControl/QGroundControl.ini`) streams centered throttle to its active
vehicle, which then fails arming with "Throttle too high". Keep it disabled.

### Camera Mapping Pipeline (OpenCV)
Each drone flies a balanced 1/n serpentine strip of the field
(`split_serpentine` in `mission/points_distributor.py` — exactly n contiguous chunks,
sizes differ by ≤1, nothing dropped; the old `split_by_grid` was unbalanced and
silently dropped waypoints for non-square drone counts). All drones share one
field origin (`field_origin_lat/lon` params, set by the launch file from
`core/config.py`, the same origin SITL homes use) so the strips tile a single
field instead of shifting with each drone's home.

The camera is an **extension**, at both layers:
- Models: `base_drone_cam{,_1,_2,_3}` wrap the plain `base_drone*` models
  (iris_with_gimbal pattern: `<include>` + fixed joint) and add a down-facing
  camera streaming H.264/RTP via GstCameraPlugin on UDP `5600 + instance`.
  The world references the `_cam` wrappers; swap back to `base_drone*` to fly
  camera-less. GstCameraPlugin only streams after a Boolean(true) on its
  `.../image/enable_streaming` gz topic — `start_gazebo.sh` does this
  automatically.
- Nodes: `nodes/camera_drone.py` (executable `camera_drone_dds.py`) defines `CameraDrone(BaseDrone)` which overrides
  the `on_waypoint_reached` hook to capture a geotagged frame (+ ArUco
  detection) per waypoint into `/root/logs/drone_<id>/` (host: `./logs`).
  `BaseDrone` stays camera-free; camera failures never break the mission.
  The capture uses OpenCV's GStreamer backend — the container needs Ubuntu's
  `python3-opencv` (pip's opencv-python lacks GStreamer).

Simulated weeds: `src/custom_gz/worlds/generate_weeds.py` generates
`models/weed_field` — oversized magenta visual-only blobs over the surveyed
80×80 m area (seeded; ground truth lat/lon in
`models/weed_field/ground_truth.json`), included by both swarm worlds.
`perception/camera_processor.py` detects them per waypoint via an HSV band
(H 140–170) + contour area filter and georeferences each detection
(nadir approximation, yaw not compensated); results land in the sidecar
JSON as `weed_detections`. Regenerate the layout with
`python3 src/custom_gz/worlds/generate_weeds.py --count N --seed S`.

Farmland visuals: the crop fields and ground plane use procedural albedo
textures (row crops, canopies with tramlines) generated by
`src/custom_gz/worlds/generate_field_textures.py` into
`models/farm_textures/textures/` (~1.3 MB of 512px PNGs, referenced as
`model://farm_textures/textures/<crop>.png`). Textures only — no extra
geometry, so render cost is unchanged even with per-drone cameras. The
palette deliberately contains no magenta so the HSV weed detector keeps an
unambiguous target; regenerate with `--seed N` after palette changes.

After a mission, build the field mosaic on the host:
```bash
python3 src/scripts/stitch_field_map.py --logs ./logs --out field_map.jpg
```

### Sprayer Drones (mixed fleet)
```bash
# 2 camera mappers + 4 sprayers (instances 2-5), verified working:
SWARM_WORLD=swarm_drone_2m4s.sdf ./start_gazebo.sh &
SPRAYER_INSTANCES="2 3 4 5" USE_GAZEBO=1 ./start_swarm.sh 6
python3 src/scripts/spray_visualizer.py --instances 2 3 4 5 &   # host
```
The sprayer is an extension at every layer, mirroring the camera:
- Models: `base_drone_sprayer_{2..5}` wrap `base_drone_{2..5}` (FDM 9022-9052)
  at REPRESENTATIVE T25-class scale (~3x iris: 0.9 m hull, 1.1 m arms with
  rotor discs, 2.4 m six-nozzle boom, large tank) — all add-on geometry is
  visual-only with negligible mass so the tuned iris dynamics are unchanged.
  Spray plumes are particle emitters on `/sprayer/<instance>/spray_cmd`
  (requires `gz::sim::systems::ParticleEmitter` world plugin — present in
  `swarm_drone_2m4s.sdf` and `swarm_drone_spray.sdf`). base_drone_4/5 exist
  for instances 4-5 (FDM 9042/9052).
- Firmware: `SPRAYER_INSTANCES` makes start_swarm pass `DRONE_ROLE=sprayer` and
  the container appends `sprayer.parm`: ArduPilot's REAL `AC_Sprayer`
  (`SPRAY_ENABLE=1`, pump = SERVO9/function 22 with speed-proportional flow,
  spinner = SERVO10/23, RC9_OPTION=15). Sized to a DJI Agras T25.
- Node: `nodes/sprayer_drone.py` (executable `sprayer_drone_dds.py`) → `SprayerDrone(BaseDrone)` toggles the sprayer
  over SERIAL1 TCP (`5762+10i`, free since GCS uses UDP) around its mission,
  using **MAV_CMD_DO_SPRAYER (216)** — param1 1=enable/0=disable, the command
  ArduPilot routes to `AC_Sprayer::run()`. Sent as COMMAND_LONG (firmware
  converts to COMMAND_INT before dispatch) and gated on a COMMAND_ACK matched
  to command 216; on a non-ACCEPTED result or no ack it falls back to
  MAV_CMD_DO_AUX_FUNCTION (218, aux function 15), which reaches the same
  `run()` via RC_Channel. DO_SPRAYER is also a valid AUTO mission item
  (`AP_Mission::start_command_do_sprayer`) — unused, we fly GUIDED.
  An ACCEPTED ack proves only that the firmware has a sprayer object: it is
  returned whenever `AP::sprayer()` is non-null, **whatever SPRAY_ENABLE is**.
  Verify with pump PWM, not the ack. The launch file is role-aware
  (`sprayer_instances` arg from `SPRAYER_INSTANCES` env via compose): mappers
  split the field among themselves at 30 m with cameras; sprayers split it
  among themselves at 15 m.
- Visuals: host-side `src/scripts/spray_visualizer.py` polls each sprayer's
  pump servo on SERIAL2 TCP (`5763+10i`) and mirrors it to the plume topics, so
  the plume reflects real firmware behaviour (off below SPRAY_SPEED_MIN, on
  while sweeping). Verified: pump PWMs 1433-1547 while spraying at 5 m/s.

Ground-test the sprayer commands without flying (SITL instance must be up):
```bash
python3 src/scripts/spray_command_test.py --instance 2 --ground-test --aux
```
It sends both commands, matches the acks, and reads SERVO9 PWM back from
SERVO_OUTPUT_RAW. `--ground-test` temporarily zeroes SPRAY_SPEED_MIN and
raises SPRAY_PUMP_MIN (restored afterwards) because AC_Sprayer will not pump
below SPRAY_SPEED_MIN — a parked vehicle stays at idle PWM no matter what you
command. Expected on a parked drone: idle/off 1100 (= SERVO9_MIN), on 1300
(= SERVO9_MIN + 25% of range).

### Prescription Plan Pipeline (targeted spraying)
Runs automatically with the mixed fleet: mappers survey and detect weeds →
`mission/prescription_planner.py` (launched by the launch file inside swarm_controller)
waits for the survey, clusters the georeferenced detections
(`--cluster-radius`), splits balanced NN-ordered shares among sprayers, and
writes `logs/prescriptions/sprayer_<i>.json` (+ `plan.geojson` for GIS) —
while the SprayerDrones **wait on the ground** (`prepare_mission` hook polls
for the file, 600 s timeout → blanket-strip fallback) and then fly ONLY the
weed targets. Verified end-to-end: 83% of ground-truth weeds covered (<5 m),
median targeting error 0.5 m.

`start_swarm_controller.sh` archives previous `logs/drone_*` + prescriptions
to `logs/run_<ts>/` at startup — stale sidecars would otherwise short-circuit
the planner with old data.

Critical bug fixed here (was in the repo from the start):
`/ap/cmd_gps_pose` expects lat/lon in **degrees** and alt in **metres** — the
firmware scales to degE7/cm itself (AP_DDS_ExternalControl.cpp). Pre-scaling
by 1e7/1000 overflowed int32 in the firmware and sent every GUIDED target
kilometres off-field. **Verify waypoint tracking by comparing the actual
world/GPS track against commanded waypoints** — takeoff ACKs and
plausible-looking QGC paths don't prove it.

Also: in Gazebo mode content placement must use world (0,0) = field GPS
origin (NOT the drone spawn cluster), and QGC's video widget binds UDP 5600 —
the same port as drone 1's camera stream (port contention footgun).

### TAK Integration (Cursor-on-Target)
```bash
TAK_URL="udp://239.2.3.1:6969" ./start_swarm.sh 4          # ATAK LAN multicast
TAK_URL="tls://tak:8089" TAK_CERT=/root/tak/c.pem TAK_KEY=/root/tak/c.key \
  TAK_CA=/root/tak/ca.pem ./start_swarm.sh 4                 # TAK Server mTLS
python3 tests/test_tak_bridge.py          # no ROS needed
```
`nodes/tak_bridge.py` (picture logic in `tak/picture.py`; launched in swarm_controller only when `TAK_URL` is set;
`tak_url` launch arg) is read-only: it opens its OWN DDS participant per drone
domain (one `rclpy.Context(domain_id=i+1)` each) on `/ap/geopose/filtered`,
`/ap/status`, `/ap/battery`, `/ap/gps_global_origin/filtered` — not MAVLink,
because QGC owns UDP 14550+i and the sprayer node / spray visualizer own
SERIAL1/2 TCP. It also watches `logs/drone_*/wp_*.json` (live weed markers)
and `logs/prescriptions/sprayer_*.json` (targets replace detections via
`t-x-d-d` deletes). `tak/cot.py` encoders are stdlib; PyTAK is optional (below). CoT `hae` is
ellipsoidal: AMSL + `TAK_GEOID_OFFSET` (default −17 m at the field origin).
Certs go in `./tak` (gitignored, mounted at `/root/tak`). AFSIM pairing
(DIS gateway, LVC split) is a design only — see `docs/TAK.md`.

### TAK simulation without Gazebo (`docs/TAK.md`)
```bash
./start_tak_sim.sh 4          # SAR (verified); SWARM_MISSION=survey wired but untested
# http://localhost:8088       (tak_viewer, compose profile "tak")
python3 tests/test_tak_sim.py
```
SITL built-in physics replace Gazebo physics. `SIM_SENSORS=synthetic` makes the
drone nodes' `make_camera()` (`perception/synthetic_camera.py`) render nadir frames from the
worlds' ground-truth JSON (mounted at `/root/sim_models`). Those frames go
through the unchanged HSV detectors and georeferencing. `CameraProcessor` gets
each frame from `_grab_frame()`, which the synthetic camera overrides. CoT goes
out via PyTAK: `pytak==7.6.1` in Dockerfile.ros2, and `TAK_TRANSPORT`
auto|pytak|stdlib selects `PytakSender` or `CotSender` (file:// always uses
`CotSender`). `tak/viewer.py` (executable `tak_viewer.py`) is a read-only PyTAK receiver serving a Leaflet
map (`src/swarm_control/viewer/index.html`).

SAR defaults in the TAK sim: `SPAWN_LAYOUT=corners` (separate launch points),
`SAR_SEARCH=bfs` (or `dfs`/`strips`; `mission/sar_search.py`, cells claimed via O_EXCL
files in logs/sar/claims), `SIM_SCENARIO=sar_scenario` (casualty plus orange
decoys) and `SIM_REALISM=1`. Person detection is `detect_person`: HSV
candidates, then a metric shape score with frame-edge rejection. Browser e2e:
`python3 tests/e2e/check_tak_viewer.py` (Playwright).
Gotcha: `read A B < <(awk 'printf ...')` under `set -e` exits silently if the
printf lacks `\n` (read returns 1 at EOF). This killed every drone container.

Gotcha: test feeds on 239.2.3.1:6969 with the default UID prefix merge into
any live mission's TAK picture. Use `TAK_UID_PREFIX` or unicast for experiments.

### Search & Rescue Mission (`docs/SAR.md`)
```bash
SWARM_WORLD=swarm_drone_sar.sdf ./start_gazebo.sh &
SWARM_MISSION=sar TAK_URL="udp://239.2.3.1:6969" USE_GAZEBO=1 ./start_swarm.sh 4
python3 tests/test_sar.py   # 4-drone mission, ROS stubbed
```
`SWARM_MISSION=sar` (compose env) switches `start_swarm_controller.sh` to
`sar_mission.launch.py`: `SearchDrone(BaseDrone)` nodes split a 120 m square
(7x7 grid, 30 m) and detect the hi-vis orange `missing_person` model
(`camera_processor.PERSON_*`, H 0–14 high-S — clear of the farm palette and
magenta weeds; `CameraProcessor(detectors=...)` now writes one
`<name>_detections` list per detector). On a sighting the drone descends to
15 m to CONFIRM, then raises THE call: `logs/sar/call.json` created with
`O_EXCL` (first caller wins). Every drone polls it every 0.5 s, aborts its
strip, and flies its own slot from `sar_coordination.rally_slot` (finder
overhead, others on a 15 m ring at 35/40/45 m); `on_scene` is judged by GPS.
Drones that finish without a find hover and listen until all others report
done (`standby_timeout`). The TAK bridge (`--mission sar`) relays the call as
a `b-r-f-h-c` CASEVAC point + ONE GeoChat broadcast. The person model carries
its own world pose — the world `<include>` must NOT set `<pose>` (it would
replace it). Regenerate: `generate_missing_person.py --seed N`.

## Architecture Overview

### Core Communication Flow
```
ArduPilot SITL ←→ DDS/Micro-ROS Agent ←→ ROS2 Nodes (swarm_control.nodes)
     ↓
MAVLink TCP (config.mavlink_tcp_port: 5760 + 10*instance, for GCS)
```

### Code Layout
The ROS package `src/swarm_control` holds one Python package, `swarm_control`,
layered (enforced by `.importlinter`; only `nodes` may import ROS, `core` is
stdlib-only):

| Layer | Modules |
|---|---|
| `core/` | `config.py` (THE deployment contract: field origin, per-instance ports / ROS domain / sysid, camera intrinsics, SAR spawn layout), `geo.py` (THE local-metres <-> GPS model, copied from ArduPilot's `Location::offset` so it matches SITL), `drone_state.py` |
| `mission/` | `points_distributor`, `prescription_planner`, `sar_coordination`, `sar_search` |
| `perception/` | `camera_processor`, `synthetic_camera` |
| `tak/` | `cot` (CoT encoding, senders), `picture` (`SwarmTakBridge`, `SinkFanout`), `viewer` |
| `nodes/` | `base_drone`, `camera_drone`, `sprayer_drone`, `search_drone`, `tak_bridge`, `time_out_retry` |

`src/swarm_control/scripts/*.py` are thin entry points only; they keep the
installed executable names (`base_drone_dds.py`, `camera_drone_dds.py`,
`sprayer_drone_dds.py`, `search_drone_dds.py`, `prescription_planner.py`,
`tak_bridge.py`, `tak_viewer.py`) so launch files, compose and
`ros2 run swarm_control <name>.py` are unchanged. Host tools import the package
by adding `src/swarm_control` to `sys.path`. Diagnostics live in
`tools/diagnostics/`.

Never hard-code the field origin, a port formula or the camera intrinsics:
import `swarm_control.core.config` (Python) or
`eval "$(python3 .../core/config.py env --instance N)"` (shell; the ArduPilot
container mounts `core/` read-only at `/root/swarm_core`). Never convert
metres <-> GPS by hand: use `swarm_control.core.geo`. `tests/test_contracts.py`
fails on either, and checks the Gazebo model SDFs (FDM ports, camera fov/size/
stream port) against `config`.

### Key Components
1. **BaseDrone** (`nodes/base_drone.py`): arm, takeoff, GPS-arrival-gated
   waypoints, RTL; extension hooks `prepare_mission` / `on_waypoint_reached`.
2. **Waypoints** (`mission/points_distributor.py`): grid/circular patterns and
   the balanced 1/n serpentine split.
3. **Docker Services**:
   - `discovery_server`: FastRTPS discovery for ROS2 networking
   - `swarm_controller`: ROS2 control nodes and launch files
   - `drone-ardu-{ID}`: ArduPilot SITL instances (dynamically scaled)
   - `micro-ros-agent-drone-{ID}`: DDS communication bridges

### Port Allocation
Authoritative source is `core/config.py` (`instance` is 0-indexed):
- MAVLink TCP (GCS/QGC):   `5760 + 10*instance`  (drone 0 = 5760, drone 1 = 5770)
- SERIAL1 / SERIAL2 TCP:   `5762 / 5763 + 10*instance` (sprayer node / spray visualizer)
- SITL:                    `5501 + 10*instance`
- MAVProxy UDP out:        `14550 + instance`
- Micro-ROS Agent / DDS:   `2019 + instance`
- Gazebo JSON:             `9002 + 10*instance`
- Camera RTP stream:       `5600 + instance`
- ROS_DOMAIN_ID:           `instance + 1`  (domain isolation per drone)
- SYSID_THISMAV:           `instance + 1`

`check_swarm_status.sh N` checks real health: a MAVLink HEARTBEAT on each MAVProxy
UDP port (reports BUSY if QGroundControl holds the port) and `ros2 node list` in each
drone's domain.

## Critical Implementation Details

### GPS and Coordinate Systems
- One field origin (`config.FIELD_ORIGIN_LAT/LON`). Gazebo mode: every SITL home
  is the origin and SITL reports GPS = home + world position. Built-in physics:
  homes ~5 m apart. `SPAWN_LAYOUT=corners`: the SAR launch points.
- All metres <-> GPS conversion goes through `core/geo.py`: ArduPilot's
  equirectangular model (111318.845 m/deg, longitude scaled at mid-latitude),
  so commanded waypoints, detections, planner output and ground truth agree
  with SITL. (Earlier code mixed 111111 m/deg, 111320 m/deg and a pyproj
  transverse Mercator.)
- Home position must be set before arming

### State Management
The `DroneState` enum lives in `core/drone_state.py`. The full set of states:
- Connection: `INITIALIZING` → `CONNECTING` → `CONNECTED`
- Pre-flight: `DISARMED` → `ARMING` → `ARMED`
- Operation: `TAKING_OFF` → `FLYING` → `RETURNING` → `LANDING` → `LANDED`
- Error: `ERROR`, `FAILSAFE`

`drone_state.py` also defines the `FlightMode` enum (ArduCopter mode numbers: GUIDED=4,
AUTO=3, RTL=6, LAND=9, etc.). State transitions are driven by ArduPilot mode/heartbeat
changes and mission progress.

### Message Types
- ArduPilot DDS messages: `GlobalPosition`, `Heartbeat`, `Altitude`, `LocalPose`
- MAVLink protocol for GCS compatibility
- Note: there is no `msg/` package with custom `.msg` definitions. `DroneState` and
  `FlightMode` are plain Python enums, not ROS2 interface messages.

### Domain Isolation
Each drone operates in its own ROS2 domain (`config.ros_domain_id(instance)`) to
prevent cross-talk between instances.

  against `tests/golden/install_layout.txt`, smokes every executable, and runs
  the ROS tests. CI (`.github/workflows/ci.yml`) runs both halves.

## Common Development Tasks

### Adding New Drone Behaviors
Subclass `BaseDrone` in a new `nodes/<name>.py` and override its hooks
(`prepare_mission`, `on_waypoint_reached`) as `CameraDrone` / `SprayerDrone` /
`SearchDrone` do; add a `main()` and a wrapper in `scripts/` for a new executable.
Keep ROS out of everything below `nodes/`.

### Modifying Waypoint Patterns
Edit `mission/points_distributor.py`:
- Implement new pattern generation functions
- Update the waypoint distribution logic

### Adjusting Drone Parameters
ArduPilot SITL parameters live in `src/swarm_control/parameters/dds_swarm.parm` (flight
modes, speeds, safety, and GPS/DDS settings). At container startup,
`start_drone_container.sh` prepends per-instance `DDS_UDP_PORT`, `SYSID_THISMAV`, and
`DDS_DOMAIN_ID` into `instance_dds.parm`, then appends `dds_swarm.parm`.

FastDDS transport config is separate, in `src/dockerfiles/config/fastdds_profile.xml`.

## Environment Variables and Configuration

Key environment variables passed by `start_swarm.sh` / `compose.yaml` to each instance:
- `INSTANCE`: 0-indexed drone identifier (drives all per-drone port/ID math)
- `NUM_DRONES`: total swarm size
- `SYSID_THISMAV`, `ROS_DOMAIN_ID`, `MICRO_ROS_AGENT_PORT`: from `core/config.py`
- `USE_GAZEBO`, `SPAWN_LAYOUT`, `SPAWN_AREA_M`, `DRONE_ROLE`: physics / spawn / role
- `RMW_IMPLEMENTATION`: DDS middleware (`rmw_fastrtps_cpp`)

The remaining ports and the SITL home are computed inside the drone container by
`config.py env` from `INSTANCE`, not passed as environment variables.

## Dependencies and Requirements

- Host system: Ubuntu 22.04+ with Docker and Docker Compose
- Gazebo simulation (runs on host, not in containers)
- Python packages: numpy, opencv (GStreamer build in the controller image), pymavlink (host tools), pytak (optional TAK transport)
- ROS2 Humble with FastRTPS or CycloneDDS

## Debugging Tips

1. Check container health: `docker ps` and verify all services are running
2. Verify ROS2 communication: Use `ros2 topic list` inside swarm_controller
3. Monitor ArduPilot: Connect QGroundControl to ports 5760+
4. Check DDS agent logs: `docker logs micro-ros-agent-drone-0`
5. Verify GPS initialization: Ensure home position is set before arming
